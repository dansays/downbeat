# Downbeat as a native iOS app — feasibility research

**Status:** exploratory research, not a plan of record.
**Researched:** 2026-07-16, against post-WWDC-2026 sources. Apple Intelligence APIs are moving fast; re-verify before building.

## The question

Could a Downbeat-like app be built as a **native Swift iOS app** that uses **Apple Music** (instead of Roon/Qobuz) and **Apple Intelligence** (instead of Claude)? Features may be implemented differently; the four capabilities that matter:

1. Compile a taste rubric via an **interview** — play the user a representative sampling of songs, thumbs up/down (no Discogs dependency).
2. **Scrape venue websites** for show calendars using Apple Intelligence, added via a share extension ("navigate to venue site → share → Add venue").
3. **Match performances/artists** against the rubric, researching the artists with Apple Intelligence.
4. Compile an **Apple Music playlist with interleaved DJ commentary** (voice still generated by ElevenLabs).

## TL;DR

| # | Capability | Verdict |
|---|------------|---------|
| 1 | Taste interview → rubric | ✅ **Fully feasible**, even for non-subscribers (30-sec previews are free to play) |
| 2 | Share-extension venue scraping with Apple Intelligence | ✅ **Feasible**, with chunking (small context window) and a foreground-scanning caveat |
| 3 | Taste matching + artist research | ⚠️ **Feasible, but only as retrieval + judgment** — the on-device model has no world knowledge; you feed it facts via tool calls |
| 4 | Apple Music playlist with interleaved commentary | ❌ **Not as a literal Apple Music playlist** (no way to put your own MP3s in one) → ✅ **as an in-app "radio show" player** |

**Bottom line: yes, the app is possible** — provided you accept two design pivots:

- **The Blue Hour lives inside the app**, as a custom player that alternates Apple Music tracks with local commentary clips — not as a playlist in the Music app. (A companion tracks-only playlist *can* be written to the user's library.)
- **"Research the artist" is architected as retrieval + judgment**, not open-ended model knowledge: your code fetches artist facts (Apple Music catalog, Wikipedia, MusicBrainz, Last.fm), and the model classifies fit against the rubric.

And two floors: the app requires an **Apple-Intelligence-capable device** (iPhone 15 Pro or later, Apple Intelligence enabled), and full-track playback requires an **active Apple Music subscription**.

## What "Apple Intelligence" actually gives a third-party app

The developer surface is the **Foundation Models framework** (iOS 26, WWDC 2025), with major expansions announced at WWDC 2026 (iOS 27 — in developer beta now, GA fall 2026).

**On-device model (iOS 26, shipping today):**

- A ~3B-parameter, 2-bit-quantized LLM — the same model powering system Apple Intelligence features. Free, no per-token cost, works offline. ([WWDC25 session 286](https://developer.apple.com/videos/play/wwdc2025/286/))
- Core APIs: `LanguageModelSession` (stateful), **`@Generable`/`@Guide` guided generation** — constrained decoding means output *structurally cannot violate your Swift schema* — a `Tool` protocol for tool calling, and streaming. ([docs](https://developer.apple.com/documentation/FoundationModels/generating-content-and-performing-tasks-with-foundation-models))
- **Context window: 4,096 tokens** on iOS 26, shared by instructions + prompt + tool definitions + schema + output ([TN3193](https://developer.apple.com/documentation/technotes/tn3193-managing-the-on-device-foundation-model-s-context-window)). iOS 27 makes it hardware-dependent — reportedly **8,192 on newer devices** — and queryable via `SystemLanguageModel.contextSize`.
- Designed-for tasks per Apple: summarization, **extraction**, classification, tagging. Explicitly **"not designed for world knowledge or advanced reasoning."** (WWDC25 session 286, verbatim.)
- No rate limits in the foreground; **background use is budgeted** and rate-limited at the OS level ([Apple forums](https://developer.apple.com/forums/thread/791086)).

**New at WWDC 2026 (iOS 27, GA fall 2026):**

- **Private Cloud Compute opened to third parties**: `LanguageModelSession(model: PrivateCloudComputeLanguageModel())` — a one-line swap to Apple's server model. **32K-token context**, reasoning levels, image input, same guided generation/tool APIs. **Free for developers under 2M first-time App Store downloads**; metered against the *end user's* iCloud account with daily per-user caps (iCloud+ raises them); no API keys. ([WWDC26 session 241](https://developer.apple.com/videos/play/wwdc2026/241/), [MacRumors](https://www.macrumors.com/2026/06/09/apple-outlines-major-ai-and-developer-tool-updates/))
- A **`LanguageModel` protocol** lets any provider back a session — Anthropic and Google are shipping conforming Swift packages. So if Apple's models underperform on a step, Claude or Gemini can be swapped into the same code path (developer handles that auth/billing).
- Rebuilt on-device model (better instruction-following/tool calling, fewer guardrail false positives), image input on high-end hardware, a **Spotlight local-RAG tool**, an **evaluations framework**, plus an **`fm` CLI and Python SDK on macOS 27 for prototyping without writing an app**.
- Custom **adapters/fine-tuning are dead-ended** (toolkit EOL'd for OS 27) — don't plan around them.

**Availability gates to design around:** Apple-Intelligence devices only (iPhone 15 Pro+, iPad/Mac M1+), user must have Apple Intelligence enabled, ~15 supported languages, and `model.availability` must be checked at runtime (`.deviceNotEligible`, `.appleIntelligenceNotEnabled`, `.modelNotReady`).

## 1. Taste interview → rubric ✅

Everything needed exists in MusicKit, and the interview even works for users **without** an Apple Music subscription:

- **Sampling material:** `MusicCatalogSearchRequest` (search), `Artist.topSongs`, and `MusicCatalogChartsRequest(genre:)` (most-played by genre) provide representative tracks per style/era. ([MusicKit docs](https://developer.apple.com/documentation/musickit))
- **Playback for the interview:** every `Song` exposes DRM-free 30-second `previewAssets` URLs, explicitly sanctioned for playback via `AVPlayer` **without a subscription** ([Apple engineer confirmation](https://developer.apple.com/forums/thread/685311)). Full-track playback needs `ApplicationMusicPlayer` + an active subscription.
- **Warm-start seeds** (subscribers, with permission): `MusicPersonalRecommendationsRequest`, recently-played, and heavy-rotation (REST) give a head start before the first thumbs-up.
- **Compiling the rubric:** classification/summarization is squarely in the on-device model's design envelope. The rubric itself can stay what it is today — a structured text document the model consumes — just stored in the app (SwiftData or a file) instead of `data/taste-rubric.md`.
- Optional: thumbs can be mirrored to Apple Music as love/dislike ratings via the REST Ratings API (`PUT /v1/me/ratings/songs/{id}`), though keeping the rubric app-local is simpler.

The interview design is arguably *better* than the Discogs approach — it captures dislikes directly instead of inferring them from absence.

## 2. "Add venue" share extension + AI scraping ✅ (with caveats)

**Adding a venue** is a mature, well-trodden pattern:

- A share extension receives the page URL, and — the nice part — an `NSExtensionJavaScriptPreprocessingFile` runs JS **inside Safari's live page** before the extension launches, so you can capture the *already-rendered* DOM (title, event markup) at add time, sidestepping the JS-rendering problem entirely for that first scan. ([Apple App Extension guide](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionScenarios.html))
- Keep the extension thin (~120 MB memory ceiling): stash URL + captured HTML in an App Group container and let the main app do the model work.

**Re-scanning venues** from the main app:

- `URLSession` + HTML-stripping first (cheap); for JS-rendered calendars, iOS 26's new **`WebPage`** class is a first-class *headless browser* — instantiate with no view, load the URL, `callJavaScript("return document.documentElement.outerHTML")` after a settle delay. ([WWDC25 session 231](https://developer.apple.com/videos/play/wwdc2025/231/), [practitioner write-up](https://folding-sky.com/blog/ios-26-macos-26-swiftui-headless-browser-webpage-webview))
- **Extraction is the model's home turf:** "extract entities" is a documented core use case, and `@Generable` guarantees schema-valid `[Show]` structs (artist/date/time). Value *correctness* still needs prompt care — enum-constrained `@Guide` fields measurably reduce hallucination per shipped-app accounts ([Drobinin](https://drobinin.com/consulting/foundation-models-apple-intelligence/putting-apple-foundation-models-in-a-real-app/)).
- **Context math is the real constraint:** a stripped venue calendar page is often 3–10K+ tokens against a 4,096-token window on iOS 26 — chunking (one session per chunk, assemble results) is Apple's official answer ([TN3193](https://developer.apple.com/documentation/technotes/tn3193-managing-the-on-device-foundation-model-s-context-window)). iOS 27's 8K on-device window helps; **PCC's 32K window mostly eliminates the problem** at the cost of requiring network + quota.

**The honest caveat — scan cadence.** Silent periodic background work is *unreliable* on iOS: `BGAppRefreshTask` (~30 s) and `BGProcessingTask` are discretionary, favor frequently-opened apps, and in production often never fire ([case study](https://mertbulan.com/programming/dont-rely-on-bgapprefreshtask-for-your-apps-business-logic)); Foundation Models inference is additionally rate-limited in the background. The realistic design is **scan on app-open** plus an explicit **"Scan now"** (iOS 26's `BGContinuedProcessingTask` lets a user-initiated scan keep running with progress UI if the app is backgrounded). Unlike the Mac CLI version, the phone won't scan while sitting in a pocket — data freshness is tied to the user opening the app.

## 3. Matching + artist research ⚠️ (feasible, re-architected)

Two halves with very different answers:

- **Judging fit against the rubric: works.** This is classification over provided text — exactly what the model is built for. Rubric + artist facts + show listing in, `@Generable` verdict (match/skip, confidence, one-line "why") out. On iOS 26 the 4K window forces a condensed rubric; PCC's 32K takes the full rubric plus research dossier comfortably.
- **"Research the artist" from the model's own knowledge: does not work on-device.** Apple is unusually explicit that the 3B model is *not* a world-knowledge model — it will not reliably know an LA jazz sideman, and asking invites confident hallucination. Apple's prescribed pattern is **tool calling**: the model calls tools *you* write, which fetch real sources — and the Apple Music catalog itself is a strong first source (artist genres, editorial notes, top songs, related artists), supplemented by Wikipedia/MusicBrainz/Last.fm APIs. The model then judges from supplied text and can cite it. (WWDC25 session 286: providing sources "can suppress hallucinations.")
- **PCC (iOS 27) upgrades the judgment quality** — bigger model, reasoning levels — but it is still not a web-search agent; your app supplies the sources either way. If Apple's models disappoint on this step, the `LanguageModel` protocol makes Claude-via-Swift-package a drop-in for just this stage.
- Minor operational note: the system safety guardrails (`guardrailViolation`) have documented false positives, reduced-but-present in the 27 cycle — handle the error gracefully rather than assuming clean runs.

Net: **the pipeline shape survives** — it's the same scan → research → judge flow Downbeat runs today, except "research" becomes deterministic fetches your app performs, with the model doing extraction and judgment on the results rather than free-form investigation.

## 4. The Blue Hour on Apple Music ❌ → in-app player ✅

**The hard fact:** there is **no way to put app-generated audio into a user's Apple Music library or playlist on iOS.** MusicKit's playlist APIs accept only catalog/library music items; the REST tracks schema allows exactly `songs`, `library-songs`, `music-videos`, `library-music-videos` — there is no upload/import endpoint of any kind, and local-file import into the library exists only via the Music app **on a Mac** (Sync Library). Nothing changed at WWDC 2026 ([session 254](https://developer.apple.com/videos/play/wwdc2026/254/) added a music picker and subscription offers — no local audio). So "an Apple Music playlist with Holloway between the tracks" is not buildable as literally specified. (A Mac-side-load workaround exists — clips added via Mac Music app become `library-songs` the app could sequence — but requiring a Mac ritual defeats the point.)

**The viable design — the same pivot Roon forced, one level deeper.** Roon's API couldn't create playlists, so Downbeat queues a zone; Apple Music can't hold your clips, so the show becomes an **in-app hybrid player**:

- `ApplicationMusicPlayer` plays full catalog tracks in-app (active subscription required), with programmatic queue control and background-audio support.
- `AVAudioPlayer`/`AVPlayer` plays the local ElevenLabs clips between tracks.
- The app's show engine alternates the two: intro clip → act's tracks → next intro → … → outro. Lock-screen/Now Playing controls are yours to wire up.

Known rough edges (all reported by developers in the field, none disqualifying): **end-of-track detection** is observation-based (watch `queue.currentEntry` / playback-state transitions) rather than a clean callback; expect a **small gap at each handoff** between the two players (MusicKit's crossfade, iOS 18+, only works *within* its own queue); manage the shared `AVAudioSession` and interruptions deliberately. True overlap/beat-matching under Apple Music streams is a restricted entitlement (the "DJ with Apple Music" program: djay, Serato, rekordbox) — sequential alternation is what a normal app gets, which is exactly what The Blue Hour is.

**Two good complements:**

- **Also write a real Apple Music playlist** — tracks only, no commentary — via `MusicLibrary.shared.createPlaylist(name:description:items:)` (iOS 16+). It syncs across the user's devices and is the moral equivalent of Roon's "Save Queue as Playlist."
- **ElevenLabs from the device is trivial** — plain REST returning MP3 (community Swift packages exist; the official Swift SDK is agents-only, not TTS). For a personal app, a **user-supplied API key in the Keychain** is the sane pattern; ship-to-strangers distribution would need a proxy backend to protect a key. Short clips fit comfortably in the free/starter tiers (~1 credit ≈ 1 character).

## Cross-cutting realities

- **Device floor:** Apple Intelligence requires iPhone 15 Pro or later (or M1+ iPad/Mac). Check `model.availability` and design a degraded path (or hard requirement) for everyone else.
- **Subscription floor:** full-track playback requires Apple Music. Previews (interview) and playlist creation work regardless.
- **Timing:** if building started now, target **iOS 27** (GA ~fall 2026) — PCC access, 8K on-device context, and refined guardrails all materially simplify features 2 and 3. On iOS 26 alone, everything still works but with more chunking and a weaker research/judgment model.
- **Cost:** $99/yr Apple Developer Program covers MusicKit (tokens are auto-generated for native apps — no JWT plumbing) and Foundation Models (on-device free; PCC free under 2M downloads, per-user daily quotas). ElevenLabs is the only metered third-party service.
- **Calendar:** matched shows can go straight into the user's calendar via EventKit's write-only permission (iOS 17+), or per-show via the zero-permission `EKEventEditViewController` — likely replacing the published `.ics` for a single-user app (write-only access can't read events back, so dedup lives in the app's own ledger, which it needs anyway).
- **Skills gap check:** nothing here requires exotic engineering — it is all first-party framework integration (MusicKit, FoundationModels, WebKit, AVFoundation, EventKit) of the kind Apple's sample code covers well. The genuinely hard parts are product-shaped: extraction quality on messy venue pages, scan-cadence UX, and the handoff gaps in the show player.

## How today's pipeline maps

| Downbeat today (Mac + Claude + Roon) | iOS app equivalent |
|---|---|
| Claude reads venue pages (`/scan-jazz`) | Share-extension DOM capture + `WebPage` headless fetch → Foundation Models guided extraction (chunked on-device, or PCC) |
| `data/taste-rubric.md` from Discogs | In-app thumbs interview over catalog previews → rubric in SwiftData |
| Claude researches artists & judges fit | App fetches artist facts (Apple Music catalog, Wikipedia/MusicBrainz/Last.fm) → model classifies via tool calling |
| `data/seen-events.json` dedup ledger | Local store (SwiftData), same `venue\|date\|artist` key |
| `ics:build` → GitHub Pages calendar | EventKit write-only inserts (or share-sheet `.ics`) |
| Roon queue + watched-folder clips | In-app hybrid player: `ApplicationMusicPlayer` + `AVAudioPlayer` |
| Qobuz catalog | Apple Music catalog |
| ElevenLabs (server-side key) | ElevenLabs (user key in Keychain) |
| Last.fm popularity ranking | `Artist.topSongs` / charts (Last.fm optional) |

## Open questions a prototype should answer first

1. **Extraction quality** of the on-device model on real (chunked) venue pages — testable *today on a Mac* with macOS 26/27's Foundation Models, and especially easily via iOS 27's `fm` CLI / Python SDK, before writing any app code.
2. **Handoff gap** size and Now-Playing behavior when alternating `ApplicationMusicPlayer` and `AVAudioPlayer` — a one-screen spike app answers this in a day.
3. **PCC daily quotas** — real but publicly unquantified; matters for how many venue scans/artist judgments a day of normal use can spend.
4. **Guardrail false-positive rate** on music/nightlife content (venue pages mention bars, late nights, occasionally edgy artist names).
